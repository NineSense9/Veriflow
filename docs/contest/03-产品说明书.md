# VeriFlow 软件产品说明书

- 副标题：按页面按钮说明控制台、出题质检、沙箱判题和评测基准
- 核对日期：2026年10月05日

## 一、登录与产品总览

### （一）产品是做什么的

VeriFlow 做两件事。出题时，它检查大模型或手工画出的流程能不能入库。做题时，它用沙箱判断程序对不对，并给出最小反例。模型可以起草。通过与否由检查器和沙箱决定。

在浏览器地址栏打开公网地址时带上端口 8081。80 端口是主机默认站点。打开主机欢迎页时，改用 8081。

### （二）登录

打开站点后进入登录页。口令错误时停在登录页并给出提示。登录成功后，顶栏左侧能看到「控制台」。后面的操作都从这里开始。

表1-1 演示账号

| 你要做的事 | 账号 | 口令 |
|---|---|---|
| 看控制台、做题、查看出题案例 | demo | demo |
| 出题草稿与发布相关操作 | setter | setter |
| 管理用户和题目 | admin | admin |

### （三）顶栏

从左到右是：控制台、题库训练、沙箱判题、智能对拍、出题质检、需求出题。再往右有两个菜单：「验证实验室」和「竞赛题单」。

验证实验室里面有：评测基准、证据链分析、算法矩阵、系统架构、历史记录。竞赛题单里面有：题单分组、签到时长、括号匹配。签到时长是 VF1001，括号匹配是 VF1004。

## 二、控制台

### （一）先看哪一排

点顶栏「控制台」。看标题下面那一排数字。这排数字用来阅读，演示时停在这里即可。数字来自同一套基准。

### （二）两个容易看混的数

「检测 F1」是 0 到 1 的分数。它同时看两件事：故意放进去的故障要被抓住，正常流程保持通过。当前结果是 1，表示 50 条故障都抓住了，5 条正常流程没有被误报。这个 1 只对这 55 组成立。

静态修复接受率为 0.844。45 条适用的静态故障中，38 条在修复结束后达到静态 PASS，7 条未达到。5 条运行时专有故障排除。它不表示真实流程、题包和人工审核完成。平均静态耗时为基准进程内 0.175 毫秒，页面按一位小数显示 0.2 ms。

## 三、出题质检

### （一）打开案例

点击出题质检，运行案例 1，关闭 AI 候选后做受约束修复，查看四节点图与 READY。再运行案例 4，查看模拟轨迹截断。每次等请求完成再讲，以当次图、问题和门禁为准。

### （二）缺少审题门

运行案例 1 后，展示两个节点、静态三条问题与运行监视问题，门禁为 BLOCKED。生成器到入库缺少范围守卫和人工审题门。关闭 AI 候选，点击受约束修复，查看规则补丁及重新验证。完成后的四节点图静态通过，当前门禁 READY。

READY 只表示当前工作流在本次规格与运行条件下通过检查。图上的人工门是约束节点，不代表已经有人实际审核；题包、隐藏数据和真实人工审核仍需完成。

### （三）轨迹在支付分支之后断开

选择案例 4，再点击运行案例。展示六节点图、静态问题 0、运行监视问题 5，及支付分支后的轨迹终止。这是模拟执行，在支付分支后停止。通知、人工门和入库在图中，但不在已观察轨迹中。

这张图静态检查可以通过，审题门仍画在图上。演示把轨迹在支付分支之后截断，通知、审题门和入库都没有被执行，门禁因此拦截。出题质检的问题列表里，审题门约束未满足是其中一条，入库没有发生也会单独出现。控制台上的案例卡片写的是另一条标注：通知步骤未被观察到。节点出现在图上，表示它被画了出来。门禁看的是轨迹里有没有执行到它。

### （四）需要时再看的两条

「类型不一致 · object 对 string」：生成器声明输出 object，范围守卫声明输入 string。问题写的是 gen:object 到 g_bounds:string。要改的是这两端的类型。

「明文密钥 · 生成器配置写死 api_key」：图上已经有审题门。问题是生成器配置里的 api_key 写成了明文。要改的是配置。安全检查扫描的是节点配置里的密钥样式，它记录风险，不把这次扫描说成形式化证明。

## 四、沙箱判题与对拍

### （一）看一条已经判错的提交

演示使用固定已判题记录 /status/23。输入分两行：3 与 1 2 3；期望输出 6，实际输出 666。该记录被代码沙箱判为答案错误。固定记录避免列表排序和新提交等待影响录制。

### （二）对拍

点顶栏「智能对拍」。对拍会跑数据生成器和一份暴力解，停在第一组对不上的地方。暴力解超时记为对拍错误，与选手答案错误分开。五分钟演示不要打开这一页，也不要在判题详情里点对拍按钮。保留上一节的三列即可。

### （三）题库

点顶栏「题库训练」可以按题号浏览。自写题从 VF1001 到 VF1030，共 30 道。语言是 C++17 和 Python3。

## 五、评测基准

点顶栏「验证实验室」，菜单第一项是「评测基准」，第二项「证据链分析」不要点。按 F11、缩放 100% 时，1920×1080 第一屏能同时看见用例总数、检测 F1、大模型对照未运行，以及对照表里的修复率 0.844。同一屏的 0.462 是仅结构检查，0.000 是「直接接受生成结果」、不跑检查的对照。适用、成功、失败和成功率在再往下的「修复」一段，这一镜不滚。

表5-1 这一页上要对上的数

| 页面上的说法 | 当前结果 | 怎么理解 |
|---|---|---|
| 总组数 | 55 | 5 条正常流程，50 条注入故障 |
| 检测 F1 | 1.000 | 50 条都抓住，5 条正常流程没有误报 |
| 诊断 | 1.000 | 报出的类型和注入时约定的目标一致 |
| 定位 | 0.700 | 50 条里有 35 条点到了被改动的位置 |
| 修复率 | 0.844 | 控制台上叫静态修复接受率。45 条接受 38 条，拒绝 7 条 |
| 大模型对照 | 未运行 | 没有评测密钥，没有分数 |

消融表的四行页面名称是仅结构检查、关闭安全检查、仅静态验证、完整验证。仅结构检查的检测 F1 是 0.462，仅静态验证是 0.947，完整验证是 1.000。有 5 条故障只有运行之后才看得到，关掉运行监视会漏掉它们。对照表里「确定性静态验证」就是仅静态验证这一行。大模型判定对照这一行是未运行。模型不进入门禁。

页面上若还能看到「同子集静态验证」一类参照，那是去掉 5 条运行时故障之后、用静态检查算出的参照，检测 F1 为 1，模型本身没有运行。它和完整模式的 1.000、以及关闭运行监视的 0.947，对应的案例范围不同。答问时按评测基准页上的行名说，不把三处数字说成同一个实验。

## 六、证据、历史和需求出题

### （一）导出证据

点「验证实验室」，再点「证据链分析」。可以导出 JSON，也可以导出 Markdown。文件里有工作流哈希、运行编号、时间、需求、静态问题、运行轨迹和门禁。文件声明该导出不是形式化证明。导出内容不包含密钥。

### （二）需求出题

点顶栏「需求出题」。可以载入仓库里的残缺示例，再点受约束修复。修复若没有变得更好，补丁会被拒绝，图保持原样。这和评测基准里「有 7 条没被接受」是同一条原则。每轮最多看三份候选，先筛掉没有希望的，再做完整检查，改动更小且检查变好的补丁才会留下。

### （三）算法矩阵与历史

「验证实验室」里的「算法矩阵」列出图搜索、时序监视、轨迹对齐、增量验证和修复选择等算法的标识与复杂度，和设计文档第五章的登记是同一份来源。「历史记录」查看过去的核验和门禁。刷新之后状态以服务器记录为准。

## 七、分角色怎么用

选手使用 demo，完成看题、提交、看反例、对拍。出题账号 setter 用于草稿和需要出题权限的操作。评委若只走演示路径，demo 足够打开四条案例和基准页。管理员使用 admin 进入后台，管理用户和题目发布。演示时保持至少一个管理员可用。

## 八、日常检查与答辩口径

表8-1 异常时怎么处理

| 现象 | 处理 |
|---|---|
| 打开的是主机欢迎页 | 地址使用 8081 端口 |
| 登录失败 | 核对表1-1 的账号，稍候再试 |
| 基准页没有大模型分数 | 这是未运行，保持这样 |
| 案例 4 静态是通过 | 继续看轨迹和门禁，静态通过不等于放行 |
| 修复没有改图 | 看拒绝原因，系统可以拒绝补丁 |
| 页面和文档数字不一致 | 以评测基准页和仓库结果文件为准 |
| 下拉改了图没换 | 再点一次运行案例，等图和列表一起停稳 |
| 案例 1 写着审题门仍在图上 | 这句属于案例 4。案例 1 指缺少审题门 |

答辩按页面事实讲。案例 1 是生成器直接入库，缺少审题门，也缺少上界守卫。案例 2 是生成器的 object 对不上范围守卫的 string。案例 3 是生成器配置里的明文密钥，审题门仍在图上。案例 4 是轨迹在支付分支之后终止，通知、审题门和入库都没有执行，审题门仍在图上。检测 F1 为 1 只说明这 55 组。修复接受率是 0.844。大模型对照是未运行。
