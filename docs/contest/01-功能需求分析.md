# VeriFlow 软件功能需求分析文档

- 副标题：面向大模型出题工作流的规格验证、门禁与算法训练判题
- 核对日期：2026年10月05日

## 一、赛题背景与业务目标

### （一）业务痛点

大模型已经能根据一段题意生成出题流程图，也能起草选手代码。这些输出本身还不能当作判定。只看公开样例时，隐藏数据上会失败的程序也会被判成通过。出题图可能缺审题门、把类型接错，或把密钥写进节点配置。运行轨迹也可能在图仍然完整时提前断开。若再让同一个模型给自己打分，结论不稳定，也没有可复核的证据。

VeriFlow 补上的就是判定这一段：模型可以提案，检查器负责否决。出题流程先变成带类型的工作流，再经过静态检查、运行轨迹和门禁，通过之后才入库。选手代码由沙箱执行，对错以沙箱结果为准。

### （二）建设目标

给评委和出题人一个可点击的 Web 工作台。顶栏依次能进入控制台、题库训练、沙箱判题、智能对拍、出题质检和需求出题。

把「检测是否抓到故障」「诊断是否对上故障类型」「定位是否指到被改动的位置」「补丁是否被重新检查接受」分成四件不同的事，并在同一套基准上给出可复现数字。四件事依次更具体：抓住异常，不等于报对了故障码；报对了故障码，不等于点到了被改的节点；点到了节点，也不等于补丁会被接受。

保留算法训练站能力：30 道自写题，编号 VF1001 至 VF1030，判定包含编译错误、答案错误、超时、内存超限、运行错误和通过。答案错误时给出输入、期望、实际三列。判定来自沙箱。

公网演示使用 8081 端口。80 端口留给主机默认站点。需求结论是：VeriFlow 把出题和判题收成可导出的证据，内容包括约束、轨迹和沙箱结果。

## 二、用户角色与典型场景

### （一）角色边界

系统预置三类账号。下面的口令只用于公网演示。菜单里隐藏某个入口，接口仍会按角色校验。

表2-1 用户角色与主要职责

| 角色 | 演示账号 | 主要任务 |
|---|---|---|
| 选手 | demo / demo | 看题、提交、看反例、对拍 |
| 出题 | setter / setter | 编写需求、检查出题图、受约束修复 |
| 管理员 | admin / admin | 用户与题目发布等管理操作 |

### （二）两条主路径

出题路径：需求或示例图进入工作流中间表示。中间表示是出题图的规范形式，包含节点、边、类型和配置。静态检查和运行监视给出问题与证据，受约束修复可以提出补丁，门禁决定能否放行。模型可以参与把题意编成图。最终放行由门禁决定。

做题路径：选手提交 C++17 或 Python3。沙箱先跑公开样例和隐藏数据，错了给出输入、期望、实际。对拍用生成器和暴力解，停在第一组对不上的数据。教练只在已有反例时追问，不直接贴出完整题解。普通提交不因为交了一次代码就调用大模型。

## 三、功能需求

### （一）控制台

选手和出题人登录后进入控制台，管理员进入账号页。控制台标题下方展示同一套合成变异基准的三项：检测 F1、静态修复接受率、平均静态核验。数字来自接口。

检测 F1 是 0 到 1 的分数，同时看两件事：故意放进去的故障要被抓住，正常流程保持通过。静态修复接受率表示适用静态故障中，有多少在修复结束后达到静态通过。平均静态核验是这套基准里静态检查的平均耗时，统计的是进程内检查，不含打开网页的等待时间。这三项的标签直接显示在标题下方。含义见本文件术语表和产品说明书。

### （二）出题质检

出题质检页先在「核验案例」里选定一条，再点「运行案例」，图和问题列表才会换成这一条。只改下拉时，故事板文字会先变，图和问题列表仍停在上一条。四条案例的事实以点过「运行案例」、画面停稳之后为准。

表3-1 四条核验案例

| 下拉名称 | 必须成立的事实 |
|---|---|
| 缺少审题门 · 生成器直接入库 | 图为生成器指向入库。缺审题门与上界守卫，并有规格动作未满足。补审题门。 |
| 类型不一致 · object 对 string | 生成器输出 object，下一跳范围守卫输入 string。检查结果是 gen:object 到 g_bounds:string |
| 明文密钥 · 生成器配置写死 api_key | 审题门还在图上。生成器配置里的 api_key 是明文，检查报硬编码密钥 |
| 静态全绿 · 动态沙箱断流 (典型案例) | 静态可以通过，审题门仍在图上。分支条件是 payment_status 等于 success。轨迹在支付状态分支之后终止，通知、审题门和入库都没有被执行，因此被门禁拦截 |

### （三）沙箱判题、对拍与题库

沙箱判题列表可以打开一条已经判完的错误提交，详情里能看到输入、期望、实际三列。对拍由环境执行生成器和暴力解。暴力解超时记为对拍错误，与选手答案错误分开记录。

题库可按题号浏览。自写题 30 道。竞赛题单里的「签到时长」是 VF1001，「括号匹配」是 VF1004。语言是 C++17 和 Python3。

### （四）评测基准

评测基准页展示仓库内合成变异套件的结果，并写明范围限于这套案例。页首能看到用例总数和检测 F1，说明文字里写着大模型对照的状态。没有评测密钥时，这一状态是未运行，页面不填写分数。同一套 0.844 在这一页记在对照表的「修复率」，以及后面「修复」一段的「成功率」。控制台标题下才使用「静态修复接受率」这个标签。

只做结构检查、去掉安全维、关掉运行监视这三组对照，与完整结果来自同一次运行、同一批案例。关掉运行监视的检测 F1 必须和完整结果区分开。前者在这套数据上是 0.947，后者是 1.000。

### （五）证据导出与其余入口

证据链分析可以导出 JSON 和 Markdown。导出包包含工作流哈希、运行编号、时间、来源需求、规格、静态问题与见证、运行状态与轨迹、门禁、修复记录和模型调用痕迹。包内声明该文件不是形式化证明。密钥不进入导出文件。

验证实验室里还需要算法矩阵、系统架构和历史记录。算法矩阵必须列出真实实现的算法标识、复杂度和代码位置，不能只放介绍卡片。需求出题页可以打开残缺示例并做受约束修复。修复没有变得更好时，补丁被拒绝，图保持原样。

### （六）管理

管理员可以查看用户、调整账号状态，并处理题目发布。

不能停用自己，也不能停用最后一个仍可用的管理员。

## 四、核心算法需求

算法全部在仓库内实现，可以在没有大模型密钥时完成判定。下表是需求层对能力的约定。设计文档给出每一种算法的步骤、复杂度和优化取舍。验收时既看页面，也看对应测试是否把这些约定锁住。

表4-1 核心算法需求

| 能力 | 必须满足的性质 | 预期输出 |
|---|---|---|
| 规格编译 | 默认路径不调用模型，输出可检查约束 | 工作流规格 |
| 静态多维验证 | 结构、语义、数据流、可达、安全分开记状态；未知不把总状态记成通过 | 通过、失败、警告或尚未能判定 |
| 可达性见证 | 能给出一条避开强制检查点的路径，不枚举全部路径 | 见证路径 |
| 时序监视 | 一次扫描判定约定的规则子集；观察不到的分支记为未知 | 轨迹符合性 |
| 轨迹对齐 | 并发对调不报乱序；违反偏序才记乱序 | 对齐行与偏离 |
| 增量验证 | 局部改动可缩小重跑范围；拓扑大改退回全量，并与全量结果一致 | 验证结果与是否回退 |
| 受约束修复 | 非法补丁不落地；接受前必须全量验证变好；拒绝时保留原图 | 接受或拒绝 |
| 可靠性门禁 | 读静态、运行和策略；模型不进入 | 放行、待复核或拦截 |
| 合成变异评测 | 故障按清单枚举；检测、诊断、定位、修复分开计分 | 可复现的四项数字 |
| 沙箱判定 | 隐藏数据与公开样例分开；错误时带最小反例 | 编译错误至通过 |
| 对拍 | 暴力超时与选手答案错误分开 | 第一组不一致的数据 |

检测、诊断、定位、修复接受率分开计算。大模型对照若要运行，输入只能包含需求和完整工作流，不能包含故障名、期望码、被改节点、截断点或提示。没有密钥时状态必须是未运行，不能填 0 分或满分来占位。

修复的优化需求是：每轮候选有上限，先用代价更低的筛选丢掉没有希望的补丁，再做全量验证；多份都通过时偏好改动更小的补丁。加速倍数没有测量值时，文档和页面写未测量，不推断一个倍数。

## 五、非功能需求与运行约束

### （一）可用性

界面用中文业务词。协议里的 PASS、FAIL、READY 保留英文。检测 F1、静态修复接受率第一次在文档里出现时，用一句话写明含义。控制台标题下使用这两个中文标签。页面要能在桌面宽度完成演示。空列表、检查失败、门禁拦截都给出可读状态。

### （二）部署与安全

参赛演示入口是 http://116.62.5.67:8081/ 。80 端口留给主机默认站点。大模型密钥只放在服务器环境变量里，不进前端，不进 git。没有密钥时，出题编译、起草和教练走本地回退，核心判定仍由验证器和沙箱完成。证据导出和日志不得带出密钥。

表5-1 非功能指标

| 类别 | 指标 | 说明 |
|---|---|---|
| 可访问 | 8081 可登录并走通主路径 | 80 端口保持主机默认站点 |
| 可复现 | 基准命令可重跑 | 数字以仓库内结果文件为准，禁止手填满分 |
| 可区分 | 未运行和失败分开 | 没有密钥时大模型对照是未运行 |
| 可回退 | 前端按提交号发布 | 构建失败不切换正在服务的目录 |
| 可解释 | 问题带见证路径 | 证据包声明该文件不是形式化证明 |
| 可确定 | 同一输入得到同一判定 | 门禁不读取模型采样结果 |

## 七、数据质量与边界场景

### （一）基准数据的质量要求

竞赛基准使用仓库内的合成变异，范围就是这 55 组。5 条底图在注入故障之前，静态检查必须通过，运行监视也必须通过。故障由确定的枚举生成。种子 20260919 只标记这批结果来自哪一次运行，不参与抽样。

有些故障要等运行才出现，例如在某个节点后截断轨迹，或强行走某一分支。这 5 条检查的是监视器，不进入静态修复的分母。

### （二）异常和边界

没有大模型密钥时，大模型对照记为未运行，出题编译走回退，门禁照常工作。正常流程被报成故障时，检测 F1 把这种情况算进误报，不只统计抓住了多少故障。补丁没有变得更好，或补丁本身不合法，记为拒绝，接受率下降，页面列出原因。

只做结构检查会漏掉大量故障。消融表必须列出这个差距，避免把结构规则的通过说成完整验证。n8n 只做节点和连线的子集往返。没有凭证时不连接真实 n8n，走模拟运行。Dify 未实现。

## 九、附录

### （一）附录 A：赛题能力映射

创新性落在角色隔离、多维验证、运行轨迹和可以拒绝的修复。技术实现落在自研工作流中间表示、确定性验证器、门禁和沙箱。功能完整性落在题库、提交、对拍、出题质检、基准和证据导出。应用价值落在两处：只看公开样例会漏掉的错误，由沙箱在隐藏数据上抓住；大模型画出的出题图，在入库前被拦住。

### （二）附录 B：术语

检测 F1：把「故障都被抓住」和「正常流程没有被误报」合成一个 0 到 1 的分数。两项都满分时它才是 1。它只描述这一套 55 组案例。

诊断正确率：故障案例里，报出的问题码或运行时文本与注入时约定的目标一致的比例。

定位正确率：问题列表的节点、边或见证路径碰到了被改动位置的比例。

静态修复接受率：适用的静态故障经修复结束后达到静态 PASS 的比例，为 38/45。中间候选被接受与最终静态通过分开记录，运行时专有故障排除。

门禁：根据静态结果、运行结果、严重级、未知项和覆盖率下限决定放行、待复核或拦截。模型不进入这一步。退出码 0 可以是放行，也可以是待复核。退出码 1 是拦截。退出码 2 是命令行工具错误，不是门禁判定。

工作流中间表示：出题图的规范形式，包含节点、边、类型和配置。后文与设计文档中的 WorkflowIR 指同一对象。

合成变异：在仓库里的正确底图上按清单改坏，再让验证器去抓。它自带标准答案，用来算分。结果只对这批案例有效。

尚未能判定：这一项现在下不了结论。验证总状态因此不记成通过。默认策略下，运行监视的尚未能判定只记警告，不单独拦截。安全类的尚未能判定可以拦截。当前安全检查写出的是失败，不是尚未能判定。
