## 一、部署目标与运行边界

### （一）运行目标

公网演示让评委用浏览器完成登录、出题质检、沙箱判题和评测基准。VeriFlow 监听 8081。80 端口留给主机默认站点。

### （二）哪些能力不依赖额外服务

静态验证、运行监视、门禁、受约束修复和合成变异基准都在 Python 进程里完成，不需要单独的算法服务，也不需要向量数据库。没有大模型密钥时，这些判定仍然运行。大模型只影响题意编译、可选修复提议、教练和那一项对照实验。

沙箱在公网使用 Docker 镜像 veriflow-sandbox。变量写成 docker 后，Docker 不可用就失败关闭，不会自动改成进程模式。进程模式还要求变量写成 process，并且 VERIFLOW_ENV 不是 production。评委看到的结果以公网 Docker 为准。

## 二、目标环境

表2-1 已部署环境

| 项 | 值 |
|---|---|

| Python 环境 | /opt/veriflow/.venv |

这台服务器上的 8000 端口留给其他项目。VeriFlow 的 API 使用 8010。安全组放行 8081。本机开发时 API 可以用 8000，那只是开发机，不是公网入口。

### （一）目录与版本覆盖

```
/opt/veriflow                         源码与环境文件
/opt/veriflow/web-releases/<提交号>    某一次前端构建
/opt/veriflow/deploy/release-version.env
/opt/veriflow/.env                    密钥与沙箱开关，不入库
```

release-version.env 覆盖普通环境文件的版本配置。release.py install 写入配置并重启服务，随后核对 /api/version 与打包提交一致。

## 三、新机器安装

把仓库放到 /opt/veriflow 后执行安装脚本。脚本安装依赖、在仓库目录里构建前端、写入 systemd 和 nginx。这一步的前端构建堆上限是 768M。公网更新前端不要重复这一步，改用后面的按提交号发布。Docker 不可用或镜像构建失败时，脚本不会把沙箱改成进程模式。镜像可以改用第二条命令再构建。它会把 VERIFLOW_SANDBOX 写成 docker，并重启 API。

```
bash /opt/veriflow/deploy/setup.sh
bash /opt/veriflow/deploy/build-sandbox.sh
```

## 四、环境变量

```
VERIFLOW_SANDBOX=docker
VERIFLOW_SANDBOX_IMAGE=veriflow-sandbox:latest
VERIFLOW_DB=/opt/veriflow/artifacts/veriflow.db
VERIFLOW_API_ORIGIN=http://127.0.0.1:8010
DEMO_PASSWORD=demo
SETTER_PASSWORD=setter
ADMIN_PASSWORD=admin
DEEPSEEK_API_KEY=
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-chat
```

VERIFLOW_API_ORIGIN 必须在前端构建时指向 8010。填了密钥之后重启 API，编译、起草和教练才会走云端。不填则本地回退，判定仍由验证器和沙箱完成。不要把填好的环境文件提交进 git。

## 五、按提交号更新前端

推荐在开发机按目标 API 地址预构建前端，deploy/release.py pack 打包已提交源码和 .next 构建产物。服务器 install 校验 SHA256、解包到提交目录、检查依赖、保存代码与数据库备份、切换服务，检查健康与版本。失败时恢复原配置。web-release.sh 的服务器构建为备用方式。

```
bash /opt/veriflow/deploy/web-release.sh build <40位提交号>
bash /opt/veriflow/deploy/web-release.sh activate <40位提交号>
```

本机构建后运行 python deploy/release.py pack artifacts/releases/veriflow-release.tar.gz，上传包和 SHA256。服务器运行 python3 deploy/release.py install /tmp/veriflow-release.tar.gz --sha256 <包的SHA256> --root /opt/veriflow。源码提交必须与构建一致，构建时 VERIFLOW_API_ORIGIN 指向 http://127.0.0.1:8010。

从 Windows 打包时用 git archive 且关闭 autocrlf，避免脚本变成带 CR 的换行后无法执行。

## 七、备份、回滚与排障

### （一）回滚前端

激活前脚本会保留上一份 release 配置。激活失败会写回那一份。若要主动退回，把 systemd drop-in 指回仍带 READY 的旧提交目录，再 daemon-reload 并重启 veriflow-web。不要删除当前仍可能被引用的数据库。

### （二）常见故障

表7-1 排障

| 现象 | 处理 |
|---|---|
| 浏览器是主机欢迎页 | 改用 8081 |
| 8081 返回 502 | 先看 API 是否在 8010 健康，再看前端进程 |
| 版本号不变 | 检查 release-version.env 是否写了新提交，并重启 API |
| 脚本报 bash 带 CR | 重新用 LF 打包，或在服务器上去掉 CR |
| 构建被杀掉 | 提高内存上限，不要在 1G 限制下硬跑 Next |
| 激活失败 | 先启动 API，等 8010 健康，再激活 |
| 基准没有大模型分数 | 密钥为空时就是未运行 |

```
journalctl -u veriflow-api -n 50 --no-pager
journalctl -u veriflow-web -n 50 --no-pager
```

## 八、本机开发

```
python -m pip install -e ".[dev]"
python -m pytest
python -c "import uvicorn; uvicorn.run('veriflow_api.main:app', host='127.0.0.1', port=8000, reload=True)"
```

另开一个终端，进入 apps/web，执行 npm install 和 npm run dev。浏览器打开 http://127.0.0.1:3000 ，账号 demo / demo。样例环境文件把沙箱写成 process。这里的 8000 是开发机上的 API。公网 API 是 8010。

```
python -m veriflow_cli verify --workflow examples/compose/missing_gate.json --nl "完整出题。" --explain
python -m veriflow_cli gate --workflow examples/compose/missing_gate.json --nl "完整出题。"
python scripts/competition_benchmark.py
```
